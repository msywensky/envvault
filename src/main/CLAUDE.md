# Main process internals

The cross-cutting rules (IPC, session, locks, security invariants) are in the root `CLAUDE.md`. Store and git vault internals are in `src/main/store/CLAUDE.md`.

## Push/pull flow (`src/main/sync.ts`)

- **Env files.** The unit of sync is one env file, `EnvFile = { repoName, path }` (`src/shared/types.ts`). In requests, `repoName` is always the **local folder**; the name it has in the vault can differ (Sync as, below).
  - `path` is from the repo root with `/`: `.env` for the root (`ROOT_ENV`), `apps/web/.env`, `.env.local`. `isEnvPath` (`src/core/envpath.ts`) says what's allowed at all: a name passing `isEnvFileName` (`.env` or `.env.<suffix>`, not reserved: `isReservedEnvName` in `src/shared/envrules.ts` covers `.env.bak*` and templates such as `.env.example`), at most 8 ASCII folders, no `.`, `..`, `.git`, trailing dot or device names. Whether a repo syncs a file is up to its rules (Repo settings, below).
  - Every per-file flow and IPC request takes one (`EnvPath` in `schemas.ts`). `RepoRow` is one file, with `path`, `storedName` (its vault name), `vaultName` and `local`; `path` is null only for a file entry that couldn't be decrypted.
  - **Rows are files.** Match them with `sameFile` (`src/shared/envfile.ts`) or `rowKey` (renderer), never by `name` alone, which silently mixes up a repo's files. Both compare `local` too: a folder and a repo only in the vault can share a name (a folder synced as another name, with its old entries left). `name` alone is right only for repo-level questions; the renderer groups by `repoKey` (name and `local`).
- **Finding them.** `findEnvFiles` (`src/main/git.ts`) runs three `git ls-files -z` calls with `:(glob)**/.env` and `:(glob)**/.env.*`: `--others --ignored --exclude-standard --directory` (ignored folders come back as one line and are never read), `--others --exclude-standard` (untracked and not ignored, so their pulls are refused with a reason) and `--cached` (tracked: only files named `.env` are kept, for the same reason; a committed `.env.development` is a default git already syncs). Then `isEnvPath`, which drops reserved names. Never `git status`: it refreshes the index, which can run clean filters.
  - Any git failure gives null, and the repo falls back to its root `.env` plus what the vault has.
  - What it found is cached per repo (`found` in `repos.ts`, up to `MAX_FOUND`), **whatever the repo's rules**, which are applied when listing (`scanRepos({ find, rulesFor })`, at most `MAX_FILES` per repo): a change of rules needs no rescan. `scanRepos({ find })` asks git again; `repos:list { rescan: true }` (ReposView mount, Refresh, stopping ignoring a repo) and CLI `status` do, automatic pull, mini mode and reloads after a push or pull don't. Ignored repos are never scanned.
- **Folders.** `resolveEnvDir` lstats each folder from the repo root and refuses a symlink (`readRepoFile` checks only the last component). A missing folder gives null: `vault-only` in the list, `ENV_FOLDER_MISSING` for pulls and the editor. A pull never creates a folder.
  - The git checks in `git.ts` take `dir`, the file's folder, with paths relative to it (git finds the repo by walking up), and the file's own name (`ignoreStatus(dir, name)`). `addToGitignore(repoDir, envDir, name)` adds `name` and `.env.bak.*` to the root `.gitignore` and re-checks from `envDir`.
  - Backups, the pull's temp file and the `.env.example` check are all in the file's folder.
- **The list.** `listRepos(key, vaultId, { only, find })` returns a `RepoList`: `rows`, `repos` (a `RepoInfo` per repo: every folder, then every vault name no folder syncs as, with `ignored`, `found` and `copies`) and `settings` (the defaults, every repo's own rules, and the read error, if any). Per repo that isn't ignored, its rows are its included root `.env` ∪ the included files git found ∪ the vault's entries under its vault name (file entries are decrypted to learn their path), matched by `envPathId`. A vault entry the rules exclude is a row with status `excluded` (vault info only, no local read, only Remove). The root row shows when the root `.env` is included and exists on either side, or when the repo has nothing else (the `no-env` placeholder). A symlinked `.env` in a folder that isn't in the vault is dropped (usually a link to the root one). Alldiscovered files are listed together; files in folders not yet in the valult are still shown but styled muted. `only` names a folder, or else a vault-only repo.
- **Two steps.** `previewPush`/`previewPull` return a key-name diff plus `expected: {localHash, vaultHash}`. The commit (`push`/`pull`) re-reads both sides and refuses with `LOCAL_CHANGED`/`VAULT_CHANGED` if the hashes differ from what the user reviewed. Pushing over a vault copy that changed elsewhere also needs `overwriteConfirmed`.
- **Plaintext handling.** `withSnapshot` reads the local file and the decrypted vault payload, and zero-fills the plaintext buffers afterwards.
- **Status** comes from `core/status.ts`: local vs vault vs this machine's last sync. The last sync is stored per vault in `state.json` via `src/main/state.ts`, under `lastKey(ref, folder)` (`sync.ts`).
- **Repo settings** (`src/core/vaultsettings.ts`, patterns in `src/shared/envrules.ts`).
  - **Rules** (`FileRules { include, exclude }`): a pattern without `/` is a file name matched in every folder, one with `/` a path from the repo root, and a path whose last part doesn't start with `.env` a folder and everything in it; `*` within a name, `**` any folders, case-insensitive; exclude wins (`isIncluded`). `patternProblem` validates one (fixed messages), at most `MAX_PATTERNS` per list. Shared code, so the renderer validates and previews with it.
  - **In the vault:** one entry, `settings.enc` (`snapshot.settings(keys)`, `vault.writeSettings(keys, settings, expected)`): `{ format: 1, updatedBy, updatedAt, defaults, repos: { <repoId>: { ignored?, include?, exclude? } } }`, keyed by **vault** id. A missing list uses the defaults (`effectiveRules`); `BUILT_IN_RULES` is `.env` only. Objects are `z.looseObject`, so unknown fields survive a write by this version; `format > 1` is `VAULT_NEEDS_UPDATE`. `settings()` never throws an `AppError`: a missing entry gives `emptySettings()`, an unreadable one the same plus `error` (`VAULT_TAMPERED` or `VAULT_NEEDS_UPDATE`) and its `version`, and everything (list, flows, automatic pull) then uses the built-in rules.
  - **Writes** are changes applied by `changeSettings` in `sync.ts` (`saveRepoSettings`, `saveDefaults`): read, change, compare-and-swap, and on `VAULT_CHANGED` read again and reapply, up to 3 times. Unreadable settings can't be changed; `resetSettings` overwrites only a `VAULT_TAMPERED` one. Channels: `repo:saveSettings { vaultName, ignored, include, exclude }` (by vault name), `vault:saveDefaults`, `vault:resetSettings`, `repo:setVaultName`; the renderer reads them from `repos:list`. The UI is `RepoSettingsDialog.vue`, Settings' Sync tab (`SettingsSync.vue`: the defaults, and the reset of unreadable settings; ReposView's **Defaults…** opens it) and `PatternList.vue`; ReposView lists repos with no env files and ignored repos apart.
  - **Enforced in main:** `requireSynced` refuses an ignored repo (`REPO_IGNORED`) or an excluded file (`ENV_EXCLUDED`) in every per-file flow (`withSnapshot`, the editor, `addGitignore`); `removeFromVault` refuses only ignored repos.
  - **Sync as** is this machine's: `Settings.repoNames` (`config.json`, by folder id, set only by `repo:setVaultName`; its own name clears it). `vaultNameOf(cfg, folder)` gives the vault name; `Snapshot.stored` is the vault-side file. A folder syncing as another name has its own last-sync key, `<stateKey>@<folderId>` (`lastKey`), so two checkouts keep their own status; a folder under its own name uses `stateKey(ref)`. Remove's version floor covers every folder that syncs as that name.
- **The vault.** Everything outside `src/main/vault.ts` reaches the vault through a `Vault` object (`state`, `create`, `open`, `setupCodeState`, `showSetupCode`, `snapshot`, `write`, `remove`, `writeSettings`):
  - `vaultFor(location)` gives the vault at a `VaultLocation` (`{ kind: 'folder', path }` or `{ kind: 'git', url, branch }`, `Settings.vault`);
  - `vaultAt(path)` gives the vault in a folder;
  - `vaultOn(store, secrets?)` gives the vault in any store (with this machine's secrets by default);
  - `configuredVault()` returns the one chosen in Settings, or null;
  - `requireVault()` is the same but throws `NOT_CONFIGURED`.

  `sync.ts`'s `Configured` replaces the location with the `Vault`, so sync can't reach the vault by path or URL. Switching vaults goes through `saveVault()` in `handlers.ts` (inside `exclusive()`), which locks first.

- **Setup codes (vault format 2).** A vault created with a setup code (always, in a git repository) has a 128-bit secret that is never written to the vault. Its key is `vaultKey(argon2idOutput, secret, vaultId)` (HKDF-SHA256, `core/crypto.ts`); `meta.json` adds `secretId`, a public fingerprint (`secretIdOf`, `secretMatches`), so a wrong code (`SETUP_CODE_WRONG`) is told apart from a wrong password. A format 1 vault (no setup code: a folder vault with the option unticked) derives its key from the password alone.
  - **Per machine:** `src/main/secrets.ts` keeps secrets by vault id in `<userData>/vault-secrets.json`, sealed with Electron `safeStorage`, mode `0600`. `vault.ts` takes a `VaultSecrets` (`vaultOn(store, secrets)`; `MemorySecrets` in tests). A missing or unreadable entry means the code is asked for again; no secure storage gives `SECRET_STORE_UNAVAILABLE`.
  - **Create** saves the secret before writing `meta.json` (and forgets it if that fails), and returns the code once. **Open** uses this machine's secret or a typed code (`parseSetupCode`, `core/setupcode.ts`), saved only after the key check passes. `SETUP_CODE_REQUIRED` means this machine needs it. `AppState.setupCode` is `'not-used' | 'saved' | 'needed'`; `vault:showSetupCode` returns it again while unlocked and only with the password.
  - **Tampering fails closed:** editing `meta.json` back to format 1 derives a different key (`WRONG_PASSWORD`); editing `secretId` makes the code not match.

- **Snapshots and compare-and-swap.** Reads go through `vault.snapshot()`, whose `entries` are `EntryRef`s and whose `read(keys, ref)` returns the payload, the file's `path` and its storage `version`. Take one snapshot per operation: `listRepos` uses one for every row, and `withSnapshot` (`Snapshot.vaultVersion`) one per push or pull. `vault.write(keys, file, payload, expected)` encrypts and writes only if the entry is still at that version (`null`: there is none), and otherwise throws `VAULT_CHANGED`; `saveEdit` rewords it with the editor's message. `vault.remove(ref, expected)` deletes the same way. This is on top of the content-level `expected` the user reviewed, which stays.

- **Stores and git vaults:** see `src/main/store/CLAUDE.md`.

- **Entries** (`src/main/vault.ts`). An `EntryRef` is a repo's root `.env` (`{ kind: 'root', repoId }`, stored as `<repoId>.env.enc`) or a file in its folders (`{ kind: 'file', repoId, tag }`, stored as `<repoId>.<tag>.file.enc`). `repoId` is `entryId(name)`, the **lowercased** repo name; paths are compared lowercased too (`envPathId`).
  - `entryFor(keys, file)` gives a file's ref; `entryName(ref)` its store name (shown as `RepoRow.storedName`); `stateKey(ref)` its `state.json` key (the repo id for a root entry, `<repoId>/<tag>` for a file).
  - The tag is `fileTagger` (`src/core/crypto.ts`): HMAC-SHA256 of `<repoId>/<pathId>` under an HKDF key from the vault key, first 8 bytes in hex. `withEntryKeys(key, fn)` derives one per operation and wipes it; never one per file.
  - A file entry's payload is `FilePayloadSchema`, the root schema plus `path`, with its own AAD (`envvault:file:v1:<repoId>/<tag>`). Root entries stay on `PayloadSchema`, which is strict, and `encryptPayload` writes exactly its fields. Reading a file entry refuses a `path` that is the root `.env` or doesn't give its tag (`VAULT_TAMPERED`); one whose tag matches but that `isEnvPath` doesn't accept was written with the key by a newer version (`VAULT_NEEDS_UPDATE`).
  - `settings.enc` has its own AAD (`envvault:settings:v1`) and is never an entry. The suffixes don't overlap, so a name is never ambiguous.
- **Remove from vault** (`sync.removeFromVault`, `repo:removeFromVault { vaultName, path, expectedVaultHash }`, by vault name). It needs the entry to decrypt and to still have the `expectedVaultHash` the user saw, then `vault.remove(ref, version)`. It doesn't need the repo locally (Vault only and Excluded rows are the main use), touches no local file, and sets this machine's `last` to the removed version as a floor, so a later push continues above it and machines that synced it see no rollback.
- **Errors in the list.** `listRepos` turns per-file failures (a tampered entry, a symlinked `.env`) into rows with `status: 'error'` instead of failing the whole list. A file entry that can't be read has no path to go by: its row has `path: null` and its `storedName`.
- **Raw diff.** `pullRawDiff` returns a line diff (`core/linediff.ts`) from the local `.env` to the vault copy, with only changed lines plus 3 context lines. It is masked in main (`maskEnvLines` in `core/envdiff.ts`, which shares `parseEnv`'s scanner; comments are not values and pass through) unless the request has `values: true`, which makes it return env values. It takes the same `expected` as `pull` and refuses with `LOCAL_CHANGED`/`VAULT_CHANGED` too, so it always matches the preview.
- **Resolving a conflict** (`previewMerge`/`mergeValues`/`merge` in `sync.ts`, pure logic in `src/core/envmerge.ts`, `ResolveDialog.vue`). Three-way when this machine has a base for the file, two-way otherwise.
  - **Bases** (`src/main/bases.ts`): the content this machine last synced (the synced bytes, machine-specific values blanked) per `state.json` key, in `<userData>/bases/<vaultId>/<32 hex of sha256(id)>.enc` (`0700`/`0600`). `sealBase`/`openBase` (`core/crypto.ts`): an HKDF subkey of the vault key (`envvault:base:v1`), AAD binding vault id, state id, version and hash, so `loadBase` returns only the base of exactly the recorded last sync (else null: two-way). `recordSync` in `sync.ts` writes `state.json`'s last sync and the base together, at every sync (push, pull, automatic pull, merge, Pull and mark, the list adopting an identical copy); `removeFromVault` forgets it. Saving a base never fails a sync. Stores can't import `bases` (lint).
  - **Three-way rules:** `compareEnv(local, vault, base)` gives each listed key `here`/`there` (`same`/`changed`/`added`/`removed` since the base) and `suggested` (the side that changed it; null if both did). `layoutChanged` compares each side's non-assignment, non-marker lines with the base's; `clean` means every key has a suggestion and the layout changed on at most one side. A base with a duplicate key isn't used. The dialog preselects suggestions and groups "Changed on both sides" before "Chosen for you".
  - `compareEnv(local, vault)` lists the keys that need a choice (`differs`, `local-only`, `vault-only`; local order, then vault-only in vault order) and leaves out machine-specific keys (`kept`/`unset`, from `keptKeys`, the same rule as `mergePull`). Values compare as `parseEnv` reads them. A key assigned twice in either file is `ENV_DUPLICATE_KEY`.
  - Choices cross IPC as `{ key, take: 'local' | 'vault' | 'machine' }` only. `takesFor` refuses a choice set that isn't exactly the listed keys, and `machine` on a `vault-only` key (`MERGE_INVALID`, fixed messages, `MergeError`). The merged file is `mergePull(vault, local, takes)`: the vault's layout, as on a pull, with `local` keys' local lines in the vault's position, dropped, or appended in local order, and `machine` keys kept as if marked (marker inserted). No takes is exactly the old pull. It is built in the local file's layout instead (`MergePlan.layout` in `sync.ts`) when this machine wins every key (`winsEveryKey`; `local` or `machine`), or when only the local side changed its layout since the base: `keepLocal(vault, mergeKeys(local, vault, fromVault), machine)`, i.e. the local file with the vault-chosen keys' lines put in (`mergeKeys`), plus markers for `machine` and vault-marked keys and the vault's `unset` keys appended empty. So "this machine's for all" equals a push of the file as written (`keptLocalBytes`). `merge` loads the base itself, so the layout rule never trusts the renderer. The vault side is `syncedBytes(merged)`, so a `machine` key goes up as a bare `KEY=`.
  - `previewMerge` also returns `unmarked` (`unmarkedKeys`): kept keys the vault marks and the local file doesn't. They need no choice but are a difference, so they aren't `formatOnly`; merging adds the marker locally. This is what a machine sees after another marked a key it had changed.
  - `merge` checks `expected` and hands `applyMerge` the takes. `applyMerge` refuses a rollback (`MERGE_INVALID`), checks the takes and `requirePullable`, and checks the temp and backup names (`localWriteNames`) **before** writing anything. Then it writes the vault copy (`syncedBytes(merged)`, at `s.vaultVersion`; no `overwriteConfirmed`, the dialog showed the vault's changes), then the local file (`writeLocal`, shared with `applyPull`), then `setLast`. If the local write fails, `last` stays, so the file is still a conflict.
  - **Pull and mark:** `PullRequest.mark` (optional key names; absent or empty is a plain pull). Each must be a `differs` key (`markTakes`, the pull's Changed list). With marks, `pull` goes through `applyMerge` with those keys as `machine` and the rest from the vault, so it writes the vault copy too and returns its new `vault`; `pullRawDiff` takes the same `mark`, so the diff matches. `SyncDialog` offers it on a pull with Changed keys, never on a rollback. `mergeValues` and `merge` take `ReviewedFile` (file and `expected`), so they never accept `mark`.
  - `mergeValues` returns both copies' values (`decodeValue`, as dotenv reads them) for the listed keys only, with the same `expected`.
  - Nothing is preselected (`ResolveDialog.vue`), except when `neverSynced` and every listed key is `vault-only`: the local file is most likely just older, so those start as `vault` (Add).
  - **Both changed** (`'both-changed'` in `SyncStatus`): `computeStatus` stays hash-only; `repoRows` refines a `conflict` to `both-changed` when there's a local file and a vault copy, no rollback, a base, and `compareEnv(...).clean` (`mergesCleanly`, which re-reads the local file and wipes it; any failure leaves a conflict). Its action is `merge` ("Merge…"), which opens the same `ResolveDialog` in summary mode (`preview.clean`): key names from the vault copy and from this machine, **Merge**, and **Choose key by key…** for the table.
  - Rows: a conflict with a local file offers `resolve` (`actionsFor`). The dialog's **Keep this machine's file…**/**Keep the vault's file…** show only when there's no table (rollback, `formatOnly`, or a failed preview) and open `SyncDialog` in conflict mode; with a table, the "for all" shortcuts and Save cover the same ground. Mini mode's **Merge…**/**Resolve…** sets `store.resolveFile` and leaves mini mode; `ReposView` opens the dialog once its rows have loaded.
- **Machine-specific keys.** A `# envvault:local` line directly above an assignment marks that key (`src/core/localkeys.ts`; byte wrappers and error mapping in `src/main/localkeys.ts`). Status and push use `projectEnv`, which blanks marked values to a canonical `KEY=` so differently formatted files on two machines hash the same. `Snapshot.localHash` stays the hash of the raw bytes, so `expected` catches any edit; `syncedHash` is what's compared with the vault. Pulls and `pullRawDiff` use `mergePull`: the vault copy with local lines kept for keys marked on either side. Both return `null` when there is nothing to change, meaning "use the original bytes", so files without markers still sync byte for byte. A marked key assigned twice fails with `ENV_DUPLICATE_KEY`.
- **`.env.example` checks** (`src/core/example.ts`, `checkExample` in `src/main/sync.ts`). Advisory only, and only for files named `.env`. Both previews compare the example with the `.env` you'll end up with: the raw local file on push (machine-specific values included), the merged result on pull. They return key names in `example`. The check isn't part of `expected`, the commit steps never read the example, and a file that can't be read becomes `status: 'unreadable'` instead of an error. `isTracked` runs only when there are same-value warnings, so push previews still work without git. Skipped when the `checkExample` setting is off.
- **Editing the vault copy** (`openEditor`/`saveEdit` in `src/main/sync.ts`, pure logic in `src/core/envedit.ts`).
  - `decodeValue`/`encodeValue` follow dotenv 16's parser exactly. `tests/envedit.test.ts` checks them against the real `dotenv.parse`, a pinned devDependency.
  - `applyEdits` splices changes into the original text, so untouched lines stay byte for byte. Machine-specific values can't be set from it.
  - `mark` (key names) inserts `LOCAL_MARKER` directly above each key; `saveEdit`'s `syncedBytes` then blanks the value. Refused for a key already marked or edited otherwise. Unmarking isn't offered: a local marker wins on pull and the next push marks the key again, so it's done by hand on each machine.
  - A save refuses with `VAULT_CHANGED` if the copy changed since it opened (`expectedVaultHash`), and runs `syncedBytes` like a push.
  - It never touches the local `.env` or `state.json`'s last sync, so a local `.env` shows vault-newer and is pulled as usual.
  - `src/core/envlines.ts` is the line-level scanner shared with `localkeys.ts`.
- **Automatic pull** (`src/main/autopull.ts`, `autoPull` in `src/main/sync.ts`, setting `autoPull`, default off: with it on, any push reaches this machine's `.env` files without review). It acts only on `vault-newer`, so it never merges.
  - `runAutoPull` lists repos (without asking git: only files with a vault copy can be newer there) and pulls each `vault-newer` file by `{ name, path }` through `exclusive(() => session.withKey(...))`, one file per `exclusive()`.
  - `autoPull` re-checks inside it: `computeStatus` must say `vault-newer` and `ignoreStatus` must pass. It then shares `applyPull` with `pull`.
  - It runs on a 60 s interval and on `kickAutoPull()` after unlock, a Settings save with it on, a changed editor save, and saving repo settings, defaults or a vault name. `kickAutoPull` is always called after `exclusive()` has resolved, never inside it. Ignored repos and excluded files are never `vault-newer`.
  - Pulled rows go to the renderer as `EV.autoPulled`. When the window isn't focused, `src/main/notify.ts` also shows a system notification. If that fails or isn't supported, it falls back to a Dock badge and one bounce (macOS) or a flashing taskbar button (Windows), cleared on focus.
  - macOS delivers notifications only for code-signed apps. Dev runs (ad-hoc signed Electron) and the unsigned build get Electron's `failed` event (`UNRErrorDomain error 1`), so on macOS the Dock fallback is what you'll actually see. `show()` returning means nothing: listen for `failed`.
- **Command line** (`src/cli/`, `src/main/cliserver.ts`, `src/main/clicommands.ts`, protocol in `src/shared/cli.ts`, setting `cliAccess`, default off).
  - **Transport:** `cliserver.ts` listens only while the setting is on (`setCliAccess`, called at startup and after every Settings save).
    - The address comes from `cliEndpoint(userData)` (`src/core/cliendpoint.ts`, shared with the CLI): a `0600` Unix socket on macOS, a named pipe hashed from `userData` on Windows.
    - Every request carries the token from `<userData>/cli-token`: 32 random bytes, replaced on each start, compared with `timingSafeEqual`. A Windows pipe grants Everyone read by default, so the token is what protects it.
    - One JSON line per connection, at most 64 KiB, answered with one `Result` line. Same rules as IPC: strict zod schemas, `failureOf` (`errors.ts`) for errors, no echoed input.
  - **Commands** (`clicommands.ts`): `status`, `previewPush` and `push`.
    - A file is named (`{ repo, path? }`, the root `.env` without a path), or found from the CLI's working directory (`{ dir, path? }`) by `envTargetAt` (`sync.ts`, with `repoAt` and `envFilesIn` from `repos.ts`): `path` in that repo, or else the env file the repo's rules include in the nearest folder at or above it (`.env` if there are several; `ENV_AMBIGUOUS` if none of them is `.env`), or else the root `.env`. Ignored repos give `REPO_IGNORED`. `status` returns `{ rows, ignored }`: every file of the repo (or of all), and the ignored repos' names. The protocol is `CLI_PROTOCOL` 3.
    - `push` is `sync.push` inside `exclusive(() => session.withKey(...))` with `overwriteConfirmed: false`, so it's one-sided only.
    - Pushes that changed the vault copy go to the renderer as `EV.cliPushed` rows, patched in like automatic pulls.
  - **The CLI** (`src/cli/main.ts`): two steps, like the app. `push --dry-run` prints the preview's `expected` as a token, and `push --expect <token>` sends it back. `--path` goes with `push`, with or without `--repo`. An interactive push sends back the `{ repo, path }` its preview returned, so it pushes exactly that file. Exit codes: 0 done, 1 refused or failed, 2 usage, 3 `LOCKED`, 4 `CLI_UNAVAILABLE`.
  - **The Claude Code skill:** `src/core/skill.ts` (text), `src/main/skill.ts` (install, status, remove in `~/.claude/skills/envvault`).
    - It pre-approves only `status` and `push --dry-run`, so the real push still goes through Claude Code's permission prompt.
    - Its command is `node "<path to out/cli/envvault.mjs>"`, with `app.asar.unpacked` when packaged and `--profile` under a dev profile. Settings shows it as different when that changes.
    - It is replaced only on request, and removed only if it carries `SKILL_MARKER`.
- **Mini mode** (`src/main/mini.ts`, `MiniView.vue`, setting `miniOnTop`, default on).
  - `window:setLayout` (`Layout` in `src/shared/types.ts`) switches between `full` and `mini` on one env file (`repoName`, `path`), `reviewing` while SyncDialog is open. Main owns the sizes; the renderer never sends numbers. `placeWithin` (`src/core/layout.ts`) keeps the window on its display.
  - Entering it saves the full window's normal bounds (and maximized/full screen state) and restores them on `full`. It works while locked: a compact unlock form replaces the lock screen, and a machine that needs the setup code goes back to the full window.
  - Main rechecks the file's row (`listRepos(key, id, { only })`, then `sameFile`, never the repo's first row) when the file changes (`fs.watch` on its folder, debounced), on window focus and every 60 s, through `session.withKey`, and sends it as `EV.repoStatus`. Like `EV.autoPulled`, the renderer patches it in without calling IPC.
  - Pushes and pulls still go through `SyncDialog`, never a one-click path. The Merge/Resolve dialog doesn't fit, so a file changed on both sides shows **Merge…** or **Resolve…**, which goes back to the full window and opens it there.
- **Pull safety.** Pulls require the env file and `.env.bak.*` to be git-ignored and the file to be untracked, checked by git in the file's folder. The backup is written from the bytes already read, and the temp file is named `.env.bak.tmp-<hex>` so the same ignore rule covers it. A backup is `backupName(fileName, stamp)` (`core/envpath.ts`): `.env.bak.<stamp>` for `.env`, `.env.bak.local.<stamp>` for `.env.local`. Writes are atomic via `src/main/fsutil.ts`. Backups follow the `backups` (default on) and `backupCount` (default 3, 1–50) settings: once the file is written, `pruneBackups` deletes all but the newest `backupCount` of that file's backups (`isBackupOf`: only `writeBackup`'s names for that file, never the temp file, another file's backups or other `.env.bak.*` files), best effort. Turning backups off only stops new ones.
